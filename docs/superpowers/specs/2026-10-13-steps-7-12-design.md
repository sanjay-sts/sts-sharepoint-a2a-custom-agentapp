# Design: steps 7 to 12 of the SharePoint discovery agent PoC

Date: 2026-10-13. Source: approved plan from the brainstorming session. Step numbers refer to `mvp_prd_codeinstruction.md`.

## Phase 1: step 7, two-user test (GATE)

Owner inputs to ask for in one message:
- Sites user B is a member of, and at least one B is not.
- A real file name in a site B cannot open (Q4).
- A made-up file name (Q5).
- Which site to use for Q3; owner edits one PDF there first so the 30-day filter is non-empty.

Procedure:
1. Start both servers in background terminals with output to `mcp.log` and `a2a.log`.
2. `uv run scripts/ask.py --user a "<q>"` for Q1 to Q5. One device code; cache in `.token_cache_a.json`.
3. `uv run scripts/ask.py --user b "<q>"` for Q1 to Q5. Owner completes B's device code in a **private window or separate browser profile**; `scripts/signin.py` never compares the label with the signed-in UPN, so a browser still signed in as A would put A's token in B's cache.
4. Verify each answer against `inventory.csv` (site + extension for Q2; `.pdf` + modified date for Q3). Confirm `mcp.log` shows the right caller on each request.
5. Report a 5 x 2 table with actual answers. Any B cell revealing a site or file B cannot open is a hard stop.
6. On pass: commit "Step 7: two-user test passed". Wait for owner confirmation.

Failure modes: `AADSTS65001` on B's first run = consent missing; `ERROR_AWS_CREDENTIALS:` prefix = rerun `aws sso login`.

## Phase 2: steps 8 to 12, SPFx web part

### Facts that shape this phase (verified by the planning pass; re-check at execution)
- Current SPFx is **1.23.x on Node 22** and the toolchain is **Heft, not gulp**: `heft trust-dev-cert`, `heft start`, `heft build --production`, `heft package-solution --production`. Compatibility page: https://learn.microsoft.com/en-us/sharepoint/dev/spfx/compatibility. Node 22.17 fits.
- The **hosted workbench is deprecated** (retires 1 Dec 2026) but still works today. Fallback is a site page with the Debug Toolbar query string that `heft start` prints (`?debugManifestsFile=https://localhost:4321/temp/build/manifests.js&debug=true&noredir=true`).
- **A2A wire format of this server** (`agent/a2a_server.py:168`, `create_jsonrpc_routes` with v0.3 compat off): JSON-RPC method is `"SendStreamingMessage"` (not `message/stream`), params are proto-JSON camelCase (`role: "ROLE_USER"`, `parts: [{"text": ...}]`, `messageId`), the `A2A-Version: 1.0` header is **mandatory**, SSE `data:` lines carry `{"jsonrpc","id","result":{task|statusUpdate|artifactUpdate|message}}` with default-valued fields omitted, states are `TASK_STATE_WORKING|COMPLETED|FAILED`. **Verify with a curl against the running server before writing the client**; `scripts/ask.py` is the reference behaviour.
- **Chrome/Edge 142+ Local Network Access**: calling `http://127.0.0.1` from `https://2tdgcb.sharepoint.com` shows an Allow prompt rather than a hard block; loopback is "potentially trustworthy" so mixed content is not the blocker.

### Step 8: scaffold `webpart/`
1. `npm install -g @rushstack/heft yo @microsoft/generator-sharepoint`; record versions with `npm ls -g --depth=0`.
2. `mkdir webpart && cd webpart && yo @microsoft/sharepoint`: solution `sp-agent-chat`, type WebPart, name `AgentChat`, template React, defaults otherwise. Confirm `@microsoft/sp-*` 1.23.x and `@fluentui/react` 8.x in `package.json` (add `@fluentui/react@8 --save-exact` if absent).
3. `heft trust-dev-cert` (owner accepts the Windows cert dialog).
4. Point `config/serve.json` `initialPage` at `https://2tdgcb.sharepoint.com/_layouts/15/workbench.aspx`; `heft start`.
5. Pass: empty AgentChat renders in the hosted workbench. Commit "Step 8: SPFx scaffold".

### Step 9: token and A2A client
- `webpart/config/package-solution.json`: `"webApiPermissionRequests": [{"resource": "sp-agent-poc", "scope": "access_as_user"}]`.
- `AgentChatWebPart.ts`: properties `agentUrl` (default `http://127.0.0.1:8002`) and `apiResource` (default `api://<CLIENT_ID>`, not a secret); both in the property pane and manifest `preconfiguredEntries`. Token via `this.context.aadTokenProviderFactory.getTokenProvider()` then `getToken(apiResource)`. Pass a `getToken` closure to the component.
- `a2aClient.ts` (plain `fetch`, no `@a2a-js/sdk`; ~80 lines, avoids an unverified ESM dependency in the SPFx webpack rig): POST `agentUrl/` with headers `Authorization: Bearer`, `Content-Type: application/json`, `Accept: text/event-stream`, `A2A-Version: 1.0`; body `{jsonrpc:"2.0", id, method:"SendStreamingMessage", params:{message:{role:"ROLE_USER", messageId, parts:[{text}]}}}`. Read `response.body.getReader()`, split SSE frames, ignore `:` pings, `JSON.parse` each `data:`. Dispatch: `statusUpdate` (state + message text), `artifactUpdate` where `artifact.artifactId === "answer"` (append if `append` truthy, else replace), envelope `error`. 401 -> unauthorized; non-SSE JSON -> RPC error; `TypeError` -> network. Accept an `AbortSignal`.
- **Localhost decision point**: expect the LNA prompt; owner clicks Allow. In DevTools confirm OPTIONS 200 with `access-control-allow-origin: https://2tdgcb.sharepoint.com` then POST 200 `text/event-stream`. If instead the fetch fails, show the owner the exact console line and **stop**; the fallback is Phase 3 (owner already chose AWS over dev tunnel or localhost HTTPS, but confirm before building it). If the preflight carries `Access-Control-Request-Private-Network`, the small server fix is an ASGI middleware adding `Access-Control-Allow-Private-Network: true` on OPTIONS in `agent/a2a_server.py:169-173`; raise before touching the signed-off backend.
- Pass: Network tab shows POST 200 with the bearer header; A2A log shows `caller=<user A>`. Commit "Step 9: token and A2A client".

### Step 10: chat UI (GATE)
Files under `webpart/src/webparts/agentChat/`: `a2aClient.ts`; `components/AgentChat.tsx` (state: `messages[]`, `input`, `busy`; on submit push user msg, push empty agent msg with status "Working...", `getToken` then stream); `components/MessageList.tsx` (Fluent `Stack`, `Spinner` status line, `MessageBar` errors, auto-scroll); `components/AnswerText.tsx` (markdown-lite: line split with `pre-wrap`, regex for `[label](https://...)` and bare URLs into Fluent `Link` `target=_blank rel=noopener noreferrer`, http/https only, `**` and list markers handled; no `dangerouslySetInnerHTML`, no markdown library); `components/ChatInput.tsx` (`TextField` + `PrimaryButton`, disabled while busy); minimal `.module.scss`.

Error mapping shown in a `MessageBar`:
| Condition | Visible text |
|---|---|
| `getToken` rejects | Could not get a sign-in token; API permission sp-agent-poc / access_as_user may not be approved. |
| HTTP 401 | The agent rejected the sign-in token (401). Check the API access approval. |
| fetch `TypeError` / abort | Cannot reach the agent at `<agentUrl>`. Is the A2A server running and did the browser allow local network access? |
| FAILED with `ERROR_AWS_CREDENTIALS:` | The agent's AWS credentials have expired; refresh with `aws sso login` and retry. |
| FAILED otherwise / RPC error | The message text / `code: message`. |

Pass: full round trip as user A in the workbench ("Calling list_sites..." then streamed text, links open in new tab), plus the three forced error states (A2A server stopped; wrong `apiResource`; AWS creds unset). Commit "Step 10: chat UI". Wait for owner confirmation.

### Step 11: package and deploy
1. `cd webpart && heft build --production && heft package-solution --production`; report the real path of `webpart/sharepoint/solution/sp-agent-chat.sppkg`. Confirm manifest default `agentUrl` and `includeClientSideAssets: true`.
2. Owner: upload to the tenant app catalog, enable app, SharePoint admin center > Advanced > API access > approve `sp-agent-poc / access_as_user`, add AgentChat to a modern page on one of the sites. MCP and A2A servers must be running on this machine (or Phase 3 URL set in the property).
3. Pass: the web part answers on the real page. Fill in the README web part section. Commit "Step 11: package and README".

### Step 12: final check
Owner runs Q1 to Q5 on the page as A, then as B in a separate browser profile (B also passes the LNA prompt). Report:

| # | Question | Expected A | Actual A | Pass | Expected B | Actual B | Pass | Log caller A / B |

State plainly whether any cell failed and whether B ever saw something B cannot open. Commit "Step 12: final check".

## Phase 3 (conditional): public backend on AWS, only if localhost is blocked

Owner constraint: no domain, needs HTTPS and streaming. Recommendation: **Lambda container image + Function URL with response streaming**, via AWS Lambda Web Adapter. It gives an `https://<id>.lambda-url.us-east-1.on.aws` URL with no cert or domain, supports SSE streaming (`InvokeMode: RESPONSE_STREAM`, `AWS_LWA_INVOKE_MODE=response_stream`), and Bedrock access comes from the execution role through the existing default credential chain. Alternative if cold starts or the single-container constraint bite: ECS Fargate + ALB (HTTP) fronted by CloudFront for HTTPS; more parts and monthly cost, listed only as the fallback.

Backend changes (small, after step 7 sign-off, each env-driven with current defaults so localhost keeps working):
- `agent/a2a_server.py`: `A2A_HOST`, `A2A_PORT`, `PUBLIC_URL` from env (card URL must be the Function URL).
- `mcp_server/server.py`: `MCP_HOST`/`MCP_PORT` from env (stays on 127.0.0.1 inside the container).
- Container entrypoint starts the MCP server in the background, then the A2A server on the LWA port.
- Secrets (`CLIENT_SECRET` etc.) as Lambda env vars sourced from Secrets Manager via CDK; never baked into the image.
- CORS origin unchanged (`SHAREPOINT_ORIGIN`). Bearer validation already protects the public endpoint.

Deploy with CDK (already installed) in `infra/`: ECR image from a `Dockerfile` at repo root, Lambda (Python 3.12 image, 2 GB, 15 min timeout, LWA layer or extension in image), execution role with `bedrock:InvokeModel*` on the inference profile, Function URL auth NONE. Web part `agentUrl` property set to the Function URL. Verify: `curl <url>/.well-known/agent-card.json` returns the card; `scripts/ask.py` with `A2A_URL` pointed at the Function URL streams an answer; then repeat step 9's pass check.
